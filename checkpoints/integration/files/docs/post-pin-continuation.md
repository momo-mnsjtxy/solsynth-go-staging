## Implemented behavior

- POST/DELETE `/api/posts/{id}/pin`, plus existing `/sphere` gateway aliases. POST accepts exactly one integer `mode`: 0 for publisher pages, 1 for realm pages, or 2 for the original post's reply page. Reply mode requires an actual reply and current Editor authority over the parent publisher; modes 0/1 reject replies. Null, omitted, duplicate, incorrectly cased, unknown, fractional, and contradictory fields fail before storage. DELETE requires an empty body.
- The common post projection includes nullable `pin_mode`; zero remains visible in JSON. GET `/api/posts` accepts nullable `pinned`, retaining normal date ordering and existing publisher/realm/privacy filtering.
- Writes retain the original signed proof, take canonical account, ordered realm, publisher, and post locks, compare observed ancestry after waits, read current pin mode, check current Editor/Moderator membership, and update the mode plus owned post audit in one transaction. The same proof is rechecked immediately before commit. Repeated calls are allowed and produce an audit entry.
- Pinned filtering uses read committed transactions and protects the selected roots through hydration. After acquiring scope locks it reloads rows with the full current listing predicate, and rechecks membership, pin state, and visibility after hydration. Authenticated reads revalidate their original session before commit. Private/deleted posts, disabled publishers, withdrawn memberships, and realms made private do not become visible because they are pinned. Candidate rows removed while waiting can shorten a page; no stable concurrent pagination contract is claimed.
- Moving or detaching a realm-pinned post atomically clears that realm pin, including realm-moderation removal. A publisher-page pin remains unchanged. This explicitly owned safety rule prevents old moderator rights transferring a pin to a new realm. It is recorded within the existing edit/removal transaction and audit. It is not represented as upstream parity.
- The unified host's readiness query checks `pin_mode`. Runtime SQL also requires the existing canonical `owned_post_relations` table; no relation data or authority is duplicated. The social dependency adds an explicit current realm Moderator role check.
