# Developer statistics and private custom orders

This bounded continuation adds actual composed-host routes:

- `GET /api/developers/{name}/stats` (also the existing `/develop/` service alias) returns `{"total_custom_apps": N}`.
- `POST /api/private/apps/{appId}/orders?dev={publisherName}&proj={projectId}` accepts the authored ad-hoc `identifier`, `currency`, `amount`, optional `expiration_hours` (default 24, range 1–720), `remarks`, and `meta`. Its successful response is the existing canonical commerce order with HTTP 200.

The count includes developing and suspended apps, as the authored public controller does, but never exposes their documents. Deleted apps or projects do not contribute. Deleted/shadowbanned publishers and disabled/currently punished owners are hidden using one statement snapshot. This does not invent separate app or project statistics routes.

## Source evidence and scope

Retained, licensed DysonNetwork revision `4ee2d0cebb9da8284a92483fee6dce795bf6947c` supplies `DeveloperController.GetDeveloperStats`, the complete private `CustomAppController` request/action, `CustomAppService` app/project lookup, and Wallet `PaymentService.CreateOrderAsync`. Existing manifests pin these files and their AGPL license. Authored Solian `custom_app.dart` at the existing pinned client revision establishes app display/configuration projection. `docs/developer-management-source.json` records exact paths, Git blobs and SHA-256 digests for the evidence inspected; source snapshots were not changed.

The custom-order request is different from catalog order creation: the identifier is arbitrary invoice text, not a product selector; there are no catalog items, stock reservations, recurring fulfillment, or client credentials in this request. The source explicitly disables automatic reuse. This implementation likewise creates a new order when no `Idempotency-Key` is supplied; an optional owned idempotency header gives exact replay, while different normalized terms with the same key conflict.

## Canonical transaction and explicit owned differences

The existing account proof, current session scope, current account grants and publisher editor role (50+) must all authorize `developers.apps.update`. App secrets cannot authenticate this account-management route. The developer, project and app must belong to the exact requested scope. Original proof validation, membership, ancestry locks, order insertion, outbox, idempotency and audit share one READ COMMITTED transaction. The proof and current owner are observed again after ancestry and final audit waits. No late owner-account lock is introduced after the actor/ancestry locks, matching the existing management/checkout ordering; a concurrent owner disable after the final observation may serialize after this operation.

The supported ancestry remains the canonical individual developer/publisher policy already used by app management. Imported organization/realm apps do not gain implicit authority. Creating a payable custom order requires a production app and an explicitly configured canonical merchant whose active wallet belongs to the publisher's current direct owner. These are owned admission restrictions beyond the retained controller. A missing or foreign merchant fails closed; no wallet, price, fee, entitlement or permission is synthesized.

The beneficiary wallet is captured in the order. Later merchant configuration changes cannot redirect an existing order or its idempotent replay. Payment, hold, settlement, cancellation and expiry reuse canonical commerce and its current app-owner checks. The creator is not silently made the buyer. No payment is executed by creation, and no external payment provider is called.

The explicit `internal/commercepg/custom_order_identifier.sql` migration widens the canonical order identifier column from 256 to 1,024 characters before this route is served. It is atomic, preserves nullable and existing identifiers, and refuses an unexpected prior column type or bound. The backend readiness probe requires the widened column; constructors and requests perform no DDL. The private runner applies it before either phase. The app-credential order entrance retains its prior 256-character limit; catalog product keys remain separately validated.

Amounts must be positive JSON numbers exactly representable in thousandths, including `0.001`; quoted numeric strings and extra nonzero precision are rejected. This is an explicit owned restriction: the retained Wallet service truncates to three decimals. Currency uses the authored 64-byte limit and canonical whitespace/control-character rejection. Identifier and remarks retain the authored length bounds (enforced as byte limits here). Metadata is bounded at 16 KiB and cannot inject subscription, gift, fulfillment or shipping-control keys. Unknown fields are rejected.

## Validation and remaining work

Five new required PostgreSQL cases cover canonical count visibility; actual host routing, app/publisher/project isolation and scoped editor authority; concurrent idempotency, audit rollback, exact settlement conservation, captured beneficiary and expiry; original-proof and current member/project/app/owner checks after lock waits including the final audit insert; and saved restart state. Identifier boundary coverage includes actual composed-host acceptance at 257 and 1,024 bytes and 1,025-byte rejection without partial order/audit/outbox state. An isolated synthetic legacy table exercises the exact widening migration, injected rollback, nullable-data preservation, and reapplication. The restart marker uses the existing exclusive 0600 helper, original one-hour proof and public verifier snapshot. The after phase generates no signing keys, issues no credentials, reseeds no state, and creates no replacement marker. The private CI job remains bounded at fifty minutes.

These PostgreSQL cases only compile/skip without the guarded DSN. Actual execution remains required in the coordinator's disposable private PostgreSQL CI before acceptance. New cases and marker dependencies must receive independent grouping review; this change does not silently activate group assignments.

Developer quota remains partially evidenced and unimplemented in this slice. The retained controller establishes `GET /api/develop/quota` and a generic resource-quota response, but the developer quota service, account aggregation, record shape and policy derivation have not been established by the inspected evidence. Existing `owned_bot_quotas` is publisher-scoped; this slice does not guess how to aggregate it or invent level/perk grants. Further lawful retrieval/review of the pinned authored service/callers is still possible. App/product/bot imagery and additional statistics are separate remaining flows. No excluded protocol/generated definitions, canceled repositories or unlicensed sources were used.
