# Wallet funds, red packets and raising: owned continuation

This slice resumes the preserved wallet-funds snapshot and implements the retained Wallet controller/service and authored Solian wallet screens against the existing owned Go wallet. It is an independent implementation, not a migration of an upstream wallet database. Only the licensed files already retained under `ports/wallet/accounts/source/` were consulted. No excluded Shared/protocol/generated binding, NeTo, SoSYS, Socommon or Suki source was read or imported.

## Routes and runtime

The existing backend router exposes both `/api/wallets/...` and `/wallet/wallets/...`. Added routes are `POST /funds`, creator-only `GET /funds` with bounded `offset`, `take`, numeric `status`, and `X-Total`; public `GET /funds/{id}` and `/funds/{id}/contributors`; and protected `POST /funds/{id}/receive` and `/funds/{id}/contribute`. Mutations require the named `wallets.funds.manage` permission rechecked in the same SQL transaction. `POST /funds/{id}/cancel` is an owned creator-only extension. The public-detail and contributors visibility follows the retained controller; a fund locator never grants eligibility to spend or receive.

The canonical backend and standalone `wallet-service` now compose the same transaction guard and PIN provider. Backend readiness and standalone startup require the fund schema. Both lifecycle loops run bounded fund expiry alongside existing wallet settlement. No HTTP request can supply the maintenance clock. Constructors/startup never apply schema, provision policies, mint funds or create credentials.

Apply `internal/walletpg/funds_schema.sql` explicitly after authority, canonical wallet and wallet PIN schemas. This is an additive, one-time owned schema installation, not a repeatedly executed runtime migration. Existing transaction constraints are broadened only for typed managed fund rows. The disposable runner applies it in the correct dependency order. Recover by restoring the database backup or rolling forward; never drop fund records while holds exist. Previous binaries cannot process these managed holds and must not be considered a rollback strategy.

## Backing, ledger and concurrency

Canonical `wallet_v1.pockets.amount` is spendable money and `held_amount` is reserved money. These remain the only balance store. Creating a red packet moves the exact total from availability to held amount. Each raising contribution does the same for its payer. Immutable reservation records identify this backing; remaining backing is computed from reservation amounts minus uniquely linked allocations, not from a mutable duplicate balance.

A raising contribution returns a real canonical managed frozen transaction, with both payer and captured beneficiary populated. Its ID is uniquely linked to the reservation and participant. Success atomically finalizes every contribution receipt, consumes all its held backing, credits the creator's captured wallet, and records a unique payout allocation. There is no fee, system credit, mint, nil wallet or second ledger. Contributions are one-per-account; an exact replay returns the original receipt, and changed amount/wallet returns a conflict. A replay still requires a fresh permitted payment authorization.

Red-packet claims use exact three-decimal mills. Even splits give the next claimant the ceiling share of the remaining amount and remaining slots; random shares use cryptographic rejection sampling while retaining positive backing for every remaining slot. The last claim consumes the exact residual. Closed claims require an invitation; open claims are capped. Each recipient can claim once, and a repeated claim returns its original canonical transaction.

Cancellation and expiry release only the actually unallocated reservation amounts. Partial red packets refund their remaining hold, not invitation placeholder amounts. Raising failures refund each actual contributor once, preserving its original payer wallet and canonical receipt. Successful funds are terminal and cannot refund. Refund amounts are not recalculated from the owner's current wallet selection. A same-wallet transaction is legal solely for a managed, typed, final red-packet refund. Normal transfers and ordinary transfer confirm/reject/expiry cannot change fund-managed receipts.

Fund terms, currency, target, beneficiary and expiration are immutable at the database boundary. All state-changing fund operations lock the fund row, then canonical wallets in UUID order. Creation locks its account/invitation reference set in UUID order before the canonical actor guard to avoid opposing invitations taking account foreign keys in reverse order. New contributions, claims and expiry recheck time after wallet waits. All affected pockets, receipts, reservation links, status, outbox and one-use payment proof commit or roll back together. Database allocation validation enforces source/currency/purpose, receipt identity, final status and reservation conservation.

Raising accepts only positive contributions, never overfunds, and completes exactly at the target. Fixed mode always uses its immutable configured amount, matching the retained controller/service behavior. Both open and invite-only raising funds enforce the configured participant cap of 1–512; this cap for open raising funds is an explicit owned tightening. Closed eligibility counts actual contributors, not unclaimed invitation placeholders. If fixed terms cannot reach the exact target before the cap or expiry, remaining backing is refunded on cancellation/expiry; contributions are never rounded up or silently reduced.

The selected creation-time personal wallet must belong to the creator. It becomes the raising beneficiary and cannot be replaced through the contribution body, cancellation, expiry, default-wallet changes or direct fund updates. Realm-owned campaigns are not inferred. A contribution from the beneficiary wallet itself is rejected because ordinary self transfers are not authorized. Canonical fund receipts use the existing transfer type 0, with management and allocation kinds kept in owned persistence; no unevidenced upstream System enum mapping is assumed.

## Canonical PIN policy and frontend gap

The retained create request carries `pin_code`. The retained contribute body carries only `amount`; no hidden PIN channel exists in the supplied complete authored client. Both operations use the existing canonical PIN verifier, durable attempt/lock state and transaction-bound proof. An omitted PIN succeeds only when the current canonical policy explicitly permits payment without PIN. Missing/disabled policy fails closed; configured PIN requires the correct PIN. A recently issued bearer token does not substitute for this policy.

An optional owned `pin_code` contribution field is implemented so PIN-enabled accounts can use this operation after a frontend update. Optional `payer_wallet_id` selects an actor-owned contribution wallet; omission uses the canonical default wallet. The proof binds actor, fund, payer, currency, immutable beneficiary and exact amount, and checks the current session/account/policy versions at commit. Create proof binds normalized terms and selected wallet; an optional `Idempotency-Key` prevents duplicate reservations. PIN values never enter stored fund terms, fingerprints, receipts, events or responses.

The existing amount-only Solian contribution flow requires a frontend PIN collection/update for PIN-enabled accounts. The backend does not claim that current frontend flow already works for those accounts. The client-only `/funds/recipients` and conditional `/funds/{id}/order` routes remain 404 pending further lawful reconstruction. Account-card enrichment, exact upstream error envelopes, generated-model compatibility and source-specific websocket packet identifiers remain unverified. Owned bounded fund invalidation events flow through the existing durable notification projector; they are not claimed to be upstream websocket packet parity.

## Verification and limits

Local unit and race checks cover exact-mill conservation, validation bounds, guarded service/HTTP behavior, mandatory atomic proofs, public reads, unsupported client routes and bounded outbox payloads. SQL and PL/pgSQL are syntax parsed with pglast 6.7 / PostgreSQL-major-16 grammar. SQL syntax parsing does not prove catalog/type/constraint/locking behavior.

Eleven guarded real PostgreSQL integration tests cover red-packet source routes, invitation eligibility, exact claims, fixed/random amounts, raising success and immutable beneficiary, actual hold refunds, ordinary-transfer isolation, concurrent claims/final contributions, queued final-contribution expiry, outbox rollback, create/contribution replay, canonical no-PIN/PIN policy, proof substitution/version/replay, durable rate limits, named authority and notification projection. The restart case preserves a partially funded hold, completed payouts and refunded receipts across PostgreSQL restart, then releases the preserved hold once. The runner requires all eleven before cases and the restart after case; skips cannot satisfy the CI verifier.

In this worker environment, the integration cases compile and skip because no disposable PostgreSQL DSN was supplied. No local socket retry or production connection was attempted. Actual PostgreSQL execution and restart remain for the parent's private CI, and this document makes no database pass claim until that run completes.
