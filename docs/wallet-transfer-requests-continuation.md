# Canonical wallet transfer requests

POST /api/wallets/transfer/requests and anonymous GET /api/wallets/transfer/requests/{id}, including the /wallet aliases, now compose with POST /api/wallets/transfer. The authored create body retains amount, currency, remark, wallet_id, expiration_hours (default24, range1–168), freeze and require_confirmation. The transfer_request_id branch takes all payment terms from the stored request and ignores conflicting caller amount, currency, payee, remark and lifecycle flags.

Licensed sources already retained in ports/wallet/accounts/source are WalletController.cs, PaymentService.cs and Solian__lib__wallets__wallet.dart; exact revisions/hashes and licenses remain in that source manifest. The explicit permission wallets.transfer.requests.manage is established by retained authored PERMISSIONS.md under ports/sphere/locations/source. No excluded protocol definitions or models were read. The Flutter request parser consumes IDs, amount/currency, flags, expiry and payee fields; it does not consume the original status enum. Active=0/Fulfilled=1/Expired=2 are explicitly owned numeric persistence semantics, not a claim that the excluded enum's complete wire encoding was recovered. Public endpoints only return active unexpired requests; consumed/expired requests return404.

The existing public wallet ID is an explicit prerequisite. Current wallet deletion/public-ID state and canonical recipient account/realm availability gate public reads and settlement. Canonical wallet owner/realm write policy and the named permission gate creation; at most1000 unexpired active requests per wallet are admitted. Remarks are trimmed and empty remarks normalized to null. Public response projections exclude creator account IDs and all payment credentials. Anonymous lookup performs no mutation; expired rows remain historical records until an explicit retention policy exists.

Independent internal architecture improves the original separately committed transfer/fulfillment pair: request consumption, exact canonical debit/credit or hold, ledger/outbox events and the existing short-lived PIN/payment authorization consume in one SQL transaction. Request terms are immutable. The fingerprint includes request ID without changing direct-transfer fingerprints. Missing client idempotency keys derive a request-specific key; a same-actor identical retry returns its committed transaction, while different payer/key races cannot consume the same request twice. No token/PIN enters fingerprints or request storage. Recipient authority rows use NOWAIT secondary locks; opposing activity retries instead of deadlocking. Final fulfillment rechecks expiry and public availability under locks; failure rolls back money, events, request and proof consumption.

Six guarded cases exercise source HTTP bodies, immutable server terms, anonymous projection, conservation/replay, concurrent payers, current public-ID/permission/expiry denial, precise database-constraint rollback, expiry during a wallet-row wait, and PostgreSQL restart persistence. Existing direct wallet semantics remain covered by their earlier cases. Local verification is distinct from the exact-commit private PostgreSQL run. No live money transfer, external provider, production account or credential operation occurred.
